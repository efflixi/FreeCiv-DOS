Freeciv DOS Source Cleanup Findings

Purpose:
Record the targeted source/build cleanup recommended before extending the DOS port. This document supplements checklist.txt; it is not a replacement for the full completion checklist or DOS_PORT_SPEC.md.

Assessment:
The existing source is workable as a starting point and should not be discarded or broadly rewritten. The priority is to establish trustworthy build and interface boundaries, distinguish placeholders from functional implementations, and resolve the offline engine architecture before adding substantial gameplay features.

Evidence note:
The initial findings were based on source/artifact review, without a clean cross-build or gameplay validation. Phases 1-6 established engine/transport/build/DOS/graphics/map foundations. Phase 7 verifies persistent input, reusable widgets, cooperative servicing and the normal pregame interface. Production no longer has a fatal startup gate, but new/load-game startup and gameplay remain unavailable. Component/UI success is not a playable-game claim. Verified results are recorded below and in progress.txt; historical failures do not describe the current environment without verification.

Cleanup checklist:

Execution policy:
Cleanup work follows the currently authorized Phase in checklist.txt. Check off matching items only when their complete outcomes are verified and recorded in progress.txt. Do not expand into later Phases or mark an architecture implementation complete merely because a design was selected.

1. Establish one trustworthy build path
- [x] Reproduce the intended DOS build from source with a consistent DJGPP compiler, linker, archiver, and runtime.
  - Finding: client/gui-dos-vbe/Makefile.am lists the real backend sources, but the reviewed libguiclient.a contains only dos_client_stubs.o.
  - Resolution: build-dos.sh performs fresh source/bootstrap/out-of-tree configuration/build using target GCC/Binutils/CRT, with verified archives/indexing/isolation/linkage. Repeated clean builds and source-distribution rebuild pass. Actual DOS/CWSDPMI --version and diagnostics pass; Phase 7 normal pregame/repeat launches restore text and return zero after confirmed quit.
- [x] Make backend selection, archive contents, and final executable linkage consistent.
  - Requirement: a normal DOS build must compile/link the intended implementation without relying on manually assembled archives or stale objects.
  - Resolution: clean builds link real backend/common timers/broker/isolated engine. Phase 7 adds input/widgets/commands/event loop for 33 backend members; all 10 integrated suites pass. Fresh production linkage excludes diagnostic ABI/test sources.
- [x] Establish the authoritative configure input and verify regeneration preserves DOS support.
  - Finding: configure.ac includes dos-vbe support while legacy configure.in does not.
  - Resolution: configure.ac/Makefile.am, bootstrap.sh, and the delegating autogen.sh are authoritative; legacy input switching is rejected. Generated templates and source distribution are verified, including required gettext support and all DOS/offline headers.
- [x] Verify a clean replacement before retiring existing artifacts.
  - Requirement: keep diagnostic artifacts separate from production output; do not delete the only evidence of a previously successful DOS link prematurely.
  - Resolution: new linked candidate/configuration/source distribution and evidence are retained in builds/phase2-dos/. Phase 3 deploys the hash-verified candidate, preserves the old installed client as ARCHIVE\OLDCLI.EXE, and retains named image backups. Separate runtime evidence is in builds/phase3-runtime/; this is still not a playable replacement.

2. Isolate link-only ABI stubs
- [x] Remove dos_client_stubs.c from the production linkage once working replacements are available.
  - Finding: the file duplicates GUI entry points and substitutes no-op rendering, gameplay UI, and timer functions.
  - Resolution: excluded from fresh linkage; actual backend modules satisfy declarations and common/timing.c provides timers. Persistent pregame/input/widgets now work. Remaining gameplay placeholders are not exposed as finished controls.
- [x] Compile implementations against the existing generic headers and correct incompatible signatures and function/data definitions.
  - Finding: examples include update_map_canvas, get_center_tile_mapcanvas, update_turn_done_button, and timer hooks.
  - Resolution: all real DOS modules compile under fatal interface checks, with no missing generic symbols or duplicate backend definitions. Fixed race/help signatures, missing returns/hooks, notification ownership, and command declarations.
- [ ] If link-only stubs remain useful, keep them in an explicitly separate diagnostic target.
  - Requirement: a stub executable must not be mistaken for the functional DOS backend or used as proof of gameplay.
  - Status: historical ABI-stub source is retained only as unlinked EXTRA_DIST/reference; no stub-linked diagnostic target is provided or needed for current acceptance. Distinct RTCHECK/MAPCHECK/INPUTCHK diagnostics use real code, not ABI stubs. This optional stub-target item remains unchecked.
- [ ] Replace required no-op hooks deliberately rather than deleting stubs before replacements work.
  - Partial: real graphics/map/HUD/input/widgets/chat status/pregame/command hooks replace their placeholders. City/research/diplomacy/reports/session setup and other required gameplay hooks remain future work.

3. Make incomplete functionality report its actual state
- [x] Replace placeholder VBE detection/query/set operations with real BIOS calls and verified return handling.
  - Finding: vbe_init.c reports detection/success although its BIOS functions do not invoke the BIOS.
  - Resolution: real INT 10h queries/set/current/state services and DPMI transfer storage; bounded controller/mode-list validation, decoded VBE 2/3 fields, and checked BIOS status replace all detection/query/set placeholders. Actual DOS graphics and negative BIOS-service tests are retained in builds/phase4-dos/.
- [x] Distinguish a RAM-only test framebuffer from a working graphical display.
  - Finding: framebuffer.c allocates ordinary RAM without presenting it to video memory.
  - Resolution: historical front_buffer name explicitly denotes the offscreen allocation; a distinct managed LFB mapping/LDT selector receives real presentation. Reference component pixels match at 640/800. Phase 7 also presents the persistent production GUI; no RAM-only successful display fallback remains.
- [ ] Report unavailable audio initialization/playback honestly and retain a safe no-audio mode.
  - Finding: audio_dos.c can report successful initialization or sample playback without device detection or actual output.
  - Partial: normal DOS startup explicitly forces the existing audio-none plugin and reports that choice; no hardware playback is claimed. The unselected DOS hardware plugin still requires honest implementation/audit, so this broader item remains unchecked.
- [ ] Audit required hooks for silent no-ops, invalid returns, and success-shaped placeholders.
  - Requirement: errors must remain actionable; unsupported functionality must not leave later code assuming it initialized correctly.
  - Status: obsolete fatal GUI startup gate is replaced by verified pregame/input/display behavior. Autoconnect/gameplay orders fail or report unavailable explicitly. Full gameplay/audio-hook replacement remains pending; diagnostics continue to identify their limited scope.

4. Separate demonstrations from normal execution
- [x] Move the scripted command sequence out of the normal GUI startup path and into a clearly identified test/demo path if still useful.
  - Finding: gui_main.c:ui_main() enqueues a predefined sequence, drains it, redraws, and returns instead of waiting for real input.
  - Resolution: removed the obsolete startup sequence entirely. Separate INPUTCHK exercises the real production loop with explicitly labeled fixture/pregame bridge modes; normal startup does not fabricate a game or scripted actions.
- [x] Provide a persistent user-driven event loop as the normal execution path.
  - Requirement: service input, local engine/state updates, timers, audio, and display work until the user exits.
  - Resolution: bounded 64-event FIFO, eight-event slices, real BIOS/INT33 input, 16-packet polling, timers, UI-only engine/wait service, idle yield and visible modal/pointer/chrome presentation. Normal/repeated DOS quit, keyboard fallback, fast clicks, real pregame join and native real-AI modal service are verified. Audio explicitly stays disabled.
  - Open performance follow-up: 2026-10-09 user playtest reports uneven software mouse cursor tracking. Functional for current testing, but smoothness is not verified. Measure/improve polling/presentation and idle scheduling in checklist Phases 15/16 without busy-loop regression, starvation or lost clicks; the current 55-110 ms idle gap is a likely contributor, not a measured cause.
- [x] Give shared command definitions one authoritative declaration.
  - Finding: the DOS command enum is duplicated in gui_main.c and mapview.c.
  - Resolution: gui_main.h owns the command enum/declarations and mapview.h owns dispatch; both real modules compile against the shared types.
- [ ] Remove misleading scaffold/milestone descriptions as implementations change.
  - Requirement: comments and diagnostics must describe actual behavior, not imply that scripted activity proves a live game session.
  - Partial: rewritten runtime/connect/status messages and current documentation distinguish production pregame, diagnostic map/bridge and missing session setup. Broader remaining gameplay/audio scaffolds still need review as their implementations change.

5. Correct tightly coupled interface and rendering defects
- [x] Fix missing return values and other generic-interface contract violations.
  - Finding: messagewin.c:is_meswin_open() has no return value.
  - Resolution: message/city state queries return defined FALSE while unavailable; signatures, missing generic hooks, and common-notification ownership are corrected. Verified pregame functionality replaces the fatal gate without exposing unavailable gameplay dialogs as working features.
- [x] Check framebuffer allocation, dimensions, pitch, supported formats, and size arithmetic before drawing.
  - Finding: framebuffer initialization does not report allocation failure and drawing assumes two bytes per pixel despite accepting other depths.
  - Resolution: checked 16-bit-only allocator with BIOS pitch, nonzero/signed-coordinate-compatible dimensions, even/minimum pitch, size/width overflow and explicit allocation failure; old storage is replaced only after successful allocation. VBE accepts validated RGB565 metadata. Phase 5 adds owned-size validation at primitive/presentation/readback boundaries, padding guards and failure-atomic/sanitizer tests. The broader selection/control independence item below remains incomplete.
- [x] Correct VBE mode constants and validate selected modes using BIOS metadata.
  - Finding: vbe_init.h labels standard 8-bit modes 0x101, 0x103, and 0x105 as 16-bit modes.
  - Resolution: corrected standard candidates to 0x111/0x114/0x117; actual modes are enumerated/decoded/validated rather than inferred from constants. Native tests use nonstandard IDs, VBE 2/3 pitches and reject incompatible masks/depths; actual DOS 640/800 use reported RGB565 metadata.
- [x] Convert overlays from world coordinates to viewport-relative screen coordinates and clip every write.
  - Finding: terrain uses viewport indices while unit/city/selection overlays use world coordinates; selection writes lack horizontal bounds checks.
  - Resolution: composed terrain/city/unit/selection pixels share viewport-relative coordinates and bounded writes. Requested world rectangles clip before lookup/drawing; tiny HUD dimensions and extreme signed coordinates are behaviorally tested. No direct unchecked mapview buffer writes remain.
- [x] Preserve selection independently of redraw and viewport movement.
  - Finding: map redraw resets the selected coordinates to center + (3,2).
  - Resolution: actual-state tests verify redraw/scroll/wrapping preserve selected coordinates and unit focus/position. Viewport helpers only navigate; movement commands use client controls without moving the viewport locally. Real input/event servicing remains Phase 7, outside this rendering/API check.
- [x] Validate these fixes with behavioral tests before extending the renderer or input layer.
  - Requirement: source-presence grep checks do not verify bounds, coordinates, interfaces, or device behavior.
  - Resolution: five integrated backend tests pass, including real primitive/mapview/color and low/upper VBE suites under ASan/UBSan. Exact separate RNDCHECK actual DOS640/800 output matches every pixel; dirty byte counts, Q/restoration/repeat launch and post-render engine/runtime regression pass. This validates exercised rendering fixes, not unfinished gameplay or input.

6. Resolve the offline engine architecture
- [x] Choose a local authoritative engine/action-state integration approach before substantial gameplay implementation.
  - Finding: disabling sockets does not provide game generation, AI, action validation, turns, or save/load to the client.
  - Resolution: approved isolated embedded engine and copied-byte bridge implemented in client/offline and documented in DOS_PORT_SPEC.md; real engine component tests pass natively and the harness cross-builds for DJGPP.
- [x] Define ownership and lifecycle boundaries between authoritative state and the client-visible cache.
  - Finding: existing client/server processes rely on shared globals within their separate executables; a combined runtime needs deliberate separation.
  - Resolution: separate common instances and symbol namespaces; engine owns authoritative state, broker owns transport/queues, client owns its cache. Repeated real-game/pregame cleanup tests preserve client state and pass ASan leak/error detection.
- [x] Resolve duplicate entry points, is_server definitions, shared-state assumptions, and local scheduling.
  - Requirement: simply linking server objects into the client is not a complete integration strategy.
  - Resolution: exclude the server entry point, rename engine-defined external symbols, expose only opaque APIs, and reuse cooperative startup/turn/game-over helpers rather than the blocking server loop. Production build/event-loop wiring remains in later authorized Phases.
- [x] Preserve game rules, AI behavior, fog of war, request ordering, and authoritative updates.
  - Requirement: this is architectural integration work, not cosmetic cleanup.
  - Resolution: retain rules/AI and existing packet handlers; verify capabilities, processing boundaries, ordered request IDs, player-filtered map delivery, real AI/game generation, rates updates, and turn advancement. This verifies exercised component behavior, not every gameplay action or DOS hardware behavior.

Preservation constraints:
- Leave upstream rules, AI, and reusable engine logic alone unless a specific platform/integration change is necessary.
- Do not broadly rename, reformat, or modernize unrelated code.
- Do not manually treat generated build files as authoritative before understanding their regeneration process.
- Do not remove existing artifacts until a reproducible replacement is verified.
- Preserve assets/freeciv-1.14.1-rh9/ as the unchanged extracted RPM reference; do not merge it over source data or rename its assets in place. Later DOS asset conversion/8.3 staging must be separate, retain attribution, and validate internal references. DOS_PORT_SPEC.md records the inventory; extraction alone completes no backend/packaging cleanup item.
- Keep DOS compatibility changes isolated and preserve supported non-DOS behavior.
- Address correctness and misleading success paths before cosmetic cleanup.

Recommended order:
1. Stabilize the intended build and generic-interface boundaries.
2. Resolve the offline engine design before substantial gameplay additions.
3. Implement honest DOS runtime/video initialization and persistent input/event servicing.
4. Correct renderer/resource defects and add behavioral tests.
5. Extend gameplay features on the verified foundation.

Outcome:
Keep the reusable source. Architecture/build/DOS/graphics/map foundations and Phase 7 persistent pregame/input/widgets/cooperative servicing are verified. The two scripted-loop cleanup items are complete; broad gameplay-hook/audio/scaffold audits are not. Integration corrected BIOS buffered modifiers, DJGPP zero-delay idle, lost quick mouse clicks and toolbar/map transforms without changing game rules. Evidence: builds/phase7-dos/ and progress.txt. Finish documented GitHub closeout and stop for Phase 7 review; do not begin Phase 8 without permission.
